# RViz와 실물의 큰 자세 차이: 확인된 범위

작은 엔코더 허용오차로 서로 다른 자세나 양팔 실제 접촉을 설명하지 않습니다.
아래는 기존 파일·로그·제공 영상의 읽기 분석이며 로봇/새 시뮬/테스트 실행 결과가 아닙니다.
직접 원인은 아직 확정하지 못했습니다. MoveIt 도입만으로 물리 모델 불일치가 해결되었다고 주장하지 않습니다.

## 확인된 사실

- 사고 실행 `log/meshes_real/python_19541_1794548877569.log`의 alpha 기록은 11개 표본입니다.
  명령 대비 피드백의 관절별 절대 차이 중 최대는 왼팔 1.446°, 오른팔 1.487°입니다.
- bowl_pregrasp는 5개 표본이며 최대 차이는 왼팔 1.173°, 오른팔 1.720°입니다.
  1초 기록 사이의 순간 오차·접촉 시점을 배제하는 수치는 아닙니다.
- 마지막 왼팔 명령 `[25.812,111.452,-35.393,43.953,-60.297,-16.382]°`,
  피드백 `[25.781,111.425,-35.304,44.017,-60.307,-16.384]°`였습니다.
  이 표본에서 피드백 숫자는 명령과 대체로 일치합니다.
- 드라이버의 `/joint_states_left/right`는 `GetArmJointMsgs()`의 관절 센서값에서 만들어집니다.
  명령 echo인 `GetArmJointCtrl()`는 별도 `/joint_states_ctrl_left/right`에 발행합니다.
  즉 기존 피드백 토픽을 단순히 명령 echo로 잘못 읽은 구조는 소스에서 확인되지 않았습니다.
- 명령은 이름 `joint1`~`joint6`로 SDK `JointCtrl(j1,...,j6)`에 전달됩니다.
  부호 반전·관절 순서 교환·상대각 명령 변환은 해당 드라이버 경로에 없습니다.
  최종 가드도 같은 이름 순서로 발행합니다.
- 원래 드라이버의 근사 상수는 약 0.05% 규모의 변환 차이이며, 큰 자세 변화의 설명이 아닙니다.
  현재 로컬 overlay는 정확한 pi 변환을 사용합니다. SDK 0도 명령은 이동 명령이며 영점 교정 자체가 아닙니다.
- 생성 URDF 양팔 J1~J6의 origin xyz/rpy 및 axis는 설치된
  `/home/doyeonlee/piper_ros/src/piper_description/urdf/piper_description.urdf`와 수치상 일치합니다.
  이것은 공식 파일과의 일치이며 실제 설치·교정과의 일치를 증명하지 않습니다.
- 현재 경로와 Git 기준 경로의 49개 waypoint 이름·양팔 각도·개방 폭·파지 물체는 동일합니다.
  영상 당시 RViz가 읽은 파일의 지문은 남아 있지 않으므로 영상과의 동일성을 확정할 수 없습니다.

## 큰 차이를 만들 수 있지만 아직 구분하지 못한 항목

추가 읽기 확인: 현재 시스템에 CAN 이름 고정 규칙이 없고 두 USB 어댑터는 서로 다른 시리얼을 가집니다.
현재 인터페이스/시리얼 표는 `CAN_BINDING_KO.md`에 기록했습니다. 현재 연결을 사고 당시의 좌우 배선으로
소급하지 않습니다. 번호가 바뀔 가능성과 실제로 바뀌었다는 증거를 구분합니다.

1. **논리 좌우와 물리 CAN 대응**: 래퍼는 left=can0, right=can1을 이름으로 지정합니다.
   물리 위치를 자동 식별하지 않습니다. 잘못 대응하면 명령과 피드백은 같은 CAN에서 오므로
   숫자는 일치해도 모델은 그 팔을 반대쪽 베이스에 놓고 계산합니다.
   모델 베이스 원점 간격은 175mm이므로 이 가설은 미세 허용오차와 전혀 다른 위치 오류입니다.
   알파는 양팔 동일 명령이어서 단순 좌우 교환으로 알파 자체의 떨림·이상을 전부 설명하지 못합니다.
2. **실제 베이스/관절/도구 기준과 모델 대응**: 모델은 두 베이스 RPY=[0,0,0],
   위치=[0,±0.0875,0]m, 지정된 그리퍼/마운트 고정 변환을 가정합니다.
   설치 방향·물리 영점·도구 조립 방향이 다르면 같은 관절값도 다른 외형 자세가 됩니다.
   기존 로그에는 실물 형상이나 외부 측정 좌표가 없어 어느 변환이 다른지 특정할 수 없습니다.
3. **당시 RViz가 읽은 버전 및 표시 방식**: 기존 RViz는 시간 보간된 예정 관절각을 표시했고,
   실물은 드라이버 MOVE J와 피드백 추종을 거쳤습니다. 시작 시간/속도/멈춤 동작이 달랐습니다.
   이 구조 차이는 확정됐지만 그것만으로 큰 정적 자세 차이가 발생했다고 단정할 수 없습니다.
   이전 영상에는 관절값/경로 지문/실제 동작 영상의 동시 기록이 없습니다.

그리퍼와 마운트 충돌 형상은 모델에 포함되어 있었습니다. 같은 팔 전체 제외도 확인됐지만,
양팔 간 제외는 없었으므로 그것만으로 사용자 확인 양팔 접촉을 설명할 수 없습니다.
기존 clear 표본과 최초 차단 전환의 영구 기록 부재로 감지 누락/정지 실패 역시 미확정입니다.

## 이번 소스 수정이 해소하는 부분과 남는 부분

- 새 RViz는 예정 시간표 대신 두 가드를 통과한 최종 명령의 가상 피드백으로 표시합니다.
- MoveIt OMPL 경로와 두 enforce 가드를 사용하고, 실행 경로·소스·모델·속도 지문을 고정합니다.
- 상세 로그에 좌우 목표/명령/피드백, final gate 출력, SDK command echo(수신 시),
  원본 피드백과 시각, 제어/티치 상태(메시지 패키지 제공 시), 최초 차단과 검사 자세를 기록합니다.
- 이 조치는 다음 기록에서 계획/전달/피드백 불일치를 분리하기 위한 것입니다.
  실제 CAN 위치·교정·설치 형상을 증명하지 않으며 실물 차단을 해제하지 않습니다.
- 움직임을 재현하지 않고 실제 설치·정지 자세와 해당 시각의 양팔 원본 관절값을 대응해야
  위 물리 매핑 가설을 확정/배제할 수 있습니다. 기존 자료만으로 확정됐다고 쓰지 않습니다.

실행 안내는 `SIM_START_KO.md`. 새 코드는 사용자 요청에 따라 빌드·테스트·동작 실행하지 않았습니다.

## 팔 동작 문제에 대한 추가 소스 수정 — CAN 변경 보류

사용자 최신 지시: CAN 좌우 변경은 뒤로 미루고 팔의 이상 동작을 우선 수정합니다.

- 사고 bowl_pregrasp 목표는 J4 0→62.173°, J6 0→-23.172°였습니다. 큰 손목 회전 자체가 기존 IK 목표에
  들어 있었습니다. 목표값과 피드백의 차이가 작다는 사실은 그 목표가 적절했다는 뜻이 아닙니다.
- IK는 같은 파지 위치/방향을 유지하면서 J4/J6 변화에 기본 가중치 3을 주어 작은 손목 회전을 우선합니다.
  최대 8개 해를 모으며, MoveIt에는 시작-목표 손목 범위에 기본 15° 여유만 허용하는 경로 제약을 추가했습니다.
  설정의 `planning.wrist_ik_weight`, `planning.wrist_path_margin_deg`로 명시할 수 있습니다.
  작은 회전 해나 충돌 없는 경로가 실제로 존재하는지는 실행하지 않아 확인하지 못했습니다.
- 기존 위치 목표 보간은 단계 시작/종료와 알파 감속 진입에서 속도를 즉시 바꿨습니다.
  경로 모양을 바꾸지 않는 스칼라 진행률로 정상 진행 중 목표 가속도를 제한하고 끝점/알파 감속 전에 제동합니다.
  기본 목표 가속도는 관절 20°/s², 그리퍼 20mm/s²이며 하드웨어 보증값이 아닙니다.
  실제 제어기 토크·관성·감속 정지는 이 보간기로 보증하지 않습니다. 추종/가드 대기 시 목표 진행을 멈춥니다.
- MoveIt 경로의 직선상 중간 표본만 제거하여 각 표본마다 정착 대기하는 현상을 피했습니다.
  실제 코너와 목표점은 보존하며 충돌 검사한 경로를 임의로 곡선화하지 않습니다.
- 원본 PiPER 드라이버는 각 목표에서 MotionCtrl_2(CAN, MOVE_J)를 다시 보냅니다.
  티치 모드 전환 후에도 기존 enable flag가 true이면 제어 모드를 다시 요청할 수 있는 구조였습니다.
  로컬 overlay에 모드/티치/오류/상태 신선도 검사를 넣고, 제어권 상실 이후 위치 명령을 영구 차단하도록 했습니다.
  이 차단은 현재 제어기 동작의 하드웨어 비상정지나 이미 보낸 이동 취소를 뜻하지 않습니다.
  원본 piper_ros와 현재 드라이버 프로세스에는 적용하지 않았습니다. 실물 실행 차단은 유지합니다.
- 위 문제는 코드에서 확인한 결함/개선점이며, 기존 실물의 큰 자세 불일치 및 실제 접촉의 직접 원인을
  확정했다는 뜻이 아닙니다. 새 소스의 빌드·테스트·시뮬·실물 이동은 사용자 지시에 따라 실행하지 않았습니다.
